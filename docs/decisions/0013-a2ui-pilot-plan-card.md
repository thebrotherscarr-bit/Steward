# A2UI pilot: the plan's approval card as an A2UI surface, sent beside its AG-UI interrupt

Carries out the last item of [ADR-0003](0003-ag-ui-is-the-default-transport.md)'s "Next" ("then an A2UI pilot for
approval cards only"), for one card: the plan's approval card. Accepted for that pilot scope only, on the operator's
word of 2026-11-05: "do the A2UI work, as well." Any further card, or A2UI generated by the model, is a new decision.

## Context and Problem Statement

Steward's plan card is raised by his workflow (`AskApproval`, `ctx.request_info` with an `approve_plan`
`function_approval_request`), streamed by MAF's AG-UI host as a `request_info` tool call, a CUSTOM `request_info`
event and RUN_FINISHED's interrupt, and drawn by Jesster's own card code (`AgentView.tsx`, `PhoneView.tsx`: "The
agent wants to use approve_plan" and the arguments as JSON). A2UI ("Agent-to-User Interface", google/A2UI) is an open
protocol in which an agent describes a small user interface as data (a surface: a flat list of components from a
catalog, a data model, and actions), and the client draws it with its own components. How should Steward describe the
plan card in A2UI, how does it travel, how does Jesster draw it, and how does the answer return, without breaking the
card that works today?

What ships, as read on 2026-11-05:

- **The protocol.** A2UI v0.9 (created 2025-11-20; v1.0 is the current version, and the renderers still read v0.8 and
  v0.9). A v0.9 message is `{"version": "v0.9", <one of createSurface | updateComponents | updateDataModel |
  deleteSurface>}`. `createSurface` names `surfaceId` and `catalogId` (the basic catalog's id is
  `https://a2ui.org/specification/v0_9/catalogs/basic/catalog.json`); `updateComponents` gives the flat component
  list, one of them `id: "root"`; a Button's `action` is `{"event": {"name", "context"}}`, which the client reports as
  an `action` (`name`, `surfaceId`, `sourceComponentId`, `timestamp`, `context`).
- **The renderers.** `@a2ui/react` 0.15.0 (React 18 or 19; `@a2ui/react/v0_9`: `A2uiSurface`,
  `createComponentImplementation`) with `@a2ui/web_core` 0.15.0 (`MessageProcessor(catalogs, actionHandler)`, the
  basic catalog's component APIs `ColumnApi`, `RowApi`, `TextApi`, `ButtonApi`, and `Catalog`). Since 0.10 the React
  package no longer ships React implementations of the basic catalog (they render as Web Components from
  `web_core`); an app gives its own implementations for the components it uses.
- **MAF.** `agent_framework_ag_ui` 1.7.1 ships `_a2ui` (`A2UIAgent`, `enable_a2ui`, optional extra
  `ag-ui-a2ui-toolkit`): it wraps an *agent* so that a render sub-agent (a second model call) *generates* surfaces
  through a `generate_a2ui` tool, for CopilotKit's client middleware. It does not wrap a workflow, and its surfaces are
  written by a model. For a workflow, MAF's AG-UI host passes a custom workflow event (`ctx.add_event`) to the client
  as a CUSTOM event named by the event's type, its data the value (`_workflow_run.py`, the fallback for custom
  workflow events).
- **The AG-UI binding.** The A2UI specification names AG-UI as a transport but does not define the binding.
  CopilotKit and AG2 carry operations in ACTIVITY_SNAPSHOT events (`activityType: "a2ui-surface"`); MAF's workflow
  host emits ACTIVITY_SNAPSHOT only for its own executor activity.

## Decision Drivers

- The operator's choice (ADR-0003, ARCHITECTURE section 2): the A2UI pilot is for the approval card only.
- MAF and AG-UI as they ship: no SSE written by hand, no protocol of our own beyond what the binding leaves open; the
  card's answer stays MAF's resume.
- One model (ADR-0002) and deterministic cards: the plan card is the operator's gate (RULE 6); what it shows must be
  exactly the plan that will run, not a model's rendering of it.
- Jesster's UI rules (2026-11-04): current, simple, readable, consistent; the app's own components and CSS
  variables.
- Additive: an older host, the Responses fallback, or a surface Jesster cannot draw leaves today's card.
- Every capability comes with its eval (ADR-0012, amended); every piece has a test red when unplugged.

## Considered Options

- A surface built by the workflow from the plan, sent as a MAF custom workflow event (AG-UI CUSTOM `a2ui`) just before
  the card; Jesster draws it with `@a2ui/react` and its own components for the four it uses; the answer is today's
  resume.
- MAF's `A2UIAgent` / `enable_a2ui`: a render sub-agent generates the surface.
- The surface as an ACTIVITY_SNAPSHOT (`a2ui-surface`), as CopilotKit and AG2 send it.
- No A2UI: keep Jesster's card code.

## Decision Outcome

Chosen option: "a surface built by the workflow, sent as a MAF custom workflow event", because it is the only option
that keeps the card exactly the plan (no model writes it), uses MAF's workflow host as it ships (a custom event is
MAF's documented way out of a workflow), and lets Jesster use the shipped A2UI renderer while keeping its own look.

- **Steward.** `AskApproval` emits a custom workflow event of type `a2ui`, `{"request_id": <the card's id>,
  "messages": [<A2UI v0.9 messages>]}`, just before its `request_info`. The messages are `createSurface` (surface
  `plan-<card id>`, the basic catalog) and `updateComponents` (a Column: the plan, one Text per step, a Row of two
  Buttons whose actions are `{"event": {"name": "approve" | "deny", "context": {"requestId": <id>}}}`). A pure
  function builds them from the plan the card carries, so the surface and the card cannot differ. MAF's AG-UI host
  sends the event as CUSTOM `{name: "a2ui", value: {...}}`; the Responses host does not pass custom events, so the
  fallback keeps today's card.
- **Jesster.** The AG-UI client keeps a CUSTOM `a2ui` value by its `request_id` and hands it with the interrupt of the
  same id to the card (`ApprovalRequest.a2ui`). The Agent tab (and the Phone view, where a card's line carries it)
  draws the card with `@a2ui/react`'s `A2uiSurface` over `@a2ui/web_core`'s `MessageProcessor`, with a catalog of the
  app's own React implementations of the basic catalog's Column, Row, Text and Button (their APIs from `web_core`,
  the app's classes). A Button's action `approve` or `deny` answers the card as its Allow and Deny buttons do, so the
  answer is the AG-UI resume of ADR-0003. If there is no surface, or the processor refuses it, or it fails to render,
  today's card is drawn.
- **Pinned:** `@a2ui/react` and `@a2ui/web_core` 0.15.0, the v0.9 protocol.
- **Not in this decision:** other cards (writes, commits, reviews), model-generated surfaces, the Telegram and
  WhatsApp cards (they keep their buttons), A2UI v1.0.

### Consequences

- Good, because the plan card becomes data a renderer draws, so a further card is a new surface, not new card code.
- Good, because MAF, AG-UI and the A2UI renderer are used as they ship, and the answer path is unchanged.
- Good, because a surface Jesster cannot draw degrades to today's card, so the pilot cannot block a turn.
- Bad, because the AG-UI binding for A2UI is not standardized: the CUSTOM `a2ui` event's name and shape are ours. If
  a binding is published, or MAF's workflow host learns to send A2UI activities, the event moves to it.
- Bad, because two new packages (and `zod`) enter Jesster's bundle.
- Neutral: A2UI v1.0 is current; v0.9 is read by the same renderer. Moving is a later decision.

## Validation

- Steward's gate: the AG-UI host's stream carries CUSTOM `a2ui` before the plan card's interrupt, with the card's id,
  and its messages are v0.9 for the basic catalog; red when the event is removed.
- The capability (spec 001 and `capabilities.yaml`), required, with an eval case in its own set that scores, with no
  model judge, that a real plan card carries its surface and that the surface names every step of the plan.
- Jesster's tests: the client hands the surface to the card; the card draws from the surface and answers through
  `approve`; without a surface, or with one the processor refuses, today's card is drawn. Each red when unplugged.
- [ExecPlan 0004](../plans/0004-a2ui-pilot-plan-card.md) carries it out.

## Pros and Cons of the Options

### A surface built by the workflow, sent as a MAF custom workflow event

- Good, because the card shows exactly the plan, with no model call.
- Good, because MAF's workflow host carries it as it ships (`ctx.add_event` to CUSTOM).
- Bad, because the event's name and shape are ours until a binding is standardized.

### MAF's `A2UIAgent` / `enable_a2ui`

- Good, because it is MAF's own A2UI support.
- Bad, because it wraps an agent, not Steward's workflow, and its surfaces are generated by a second model call: a
  gate card would show a model's rendering of the plan, and every card would cost a model turn.

### ACTIVITY_SNAPSHOT `a2ui-surface`

- Good, because CopilotKit and AG2 send it so.
- Bad, because MAF's workflow host does not emit it for custom events; sending it would mean writing AG-UI events by
  hand beside MAF's stream.

### No A2UI

- Good, because nothing new enters.
- Bad, because it leaves ADR-0003's plan undone against the operator's word.
